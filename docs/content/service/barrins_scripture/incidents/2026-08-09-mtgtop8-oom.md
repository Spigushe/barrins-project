## Summary

A manual backfill run:

```bash
uv run scrape --source mtgtop8 \
--output-dir /home/spigushe/archives/barrins_scripture-staging --span 70000
```

crashed the entire server — Hetrix reported the host itself down, not just
the scraper process, consistent with an OOM-kill/swap-thrash event rather
than an unhandled Python exception.

## Root cause

`scrape_mtgtop8()` ran producers and consumers as two fully sequential
phases instead of a pipeline:

1. Every producer batch (hardcoded 10 threads at a time — later changed to
   `num_threads` threads per batch, 2026-08-10, unrelated to this fix) ran
   to completion first.
   Each producer that found a scrapable, unscraped tournament id pushed the
   full parsed `BeautifulSoup` DOM tree — not just the URL or raw HTML —
   onto an **unbounded** queue.
2. Only after every batch across the whole `--span` had finished did
   consumer threads start draining that queue.

A parsed `BeautifulSoup` tree carries far more memory overhead than the
source HTML (every tag/string is a Python object with parent/sibling/
navigable-string links). With `--span 70000`, a large fraction of those ids
were new/unscraped, so tens of thousands of full DOM trees accumulated in
memory simultaneously before a single consumer had a chance to drain one.

The consumer's exit condition was also why producers had to finish first:
it broke out of its loop the instant it observed the queue as empty, with
no way to distinguish "nothing left, ever" from "nothing queued yet."
Starting consumers concurrently with producers under that logic would have
raced them into exiting immediately.

## Workaround

While the fix was being developed, the only workaround was to run smaller
`--span` backfills (e.g., 10k or 20k) that didn't exhaust memory.

```bash
for start in $(seq 1 1000 70000); do
  uv run scrape --source mtgtop8 \
    --output-dir /home/spigushe/archives/barrins_scripture-staging \
    --span 1000 --id-from $start
  sleep 5
done
```

## Fix

- **Bounded queue** (`maxsize = num_threads * 10`) instead of unbounded —
  producers now block (backpressure) once the queue is full instead of
  piling up unbounded parsed trees.
- **Real pipelining** — consumer threads start before the producer batches
  run, so the queue drains continuously instead of the whole span's worth
  of candidates sitting in memory until the last batch finishes.
- **Completion signal** — a `threading.Event` replaces the
  "queue empty → stop" check. Consumers poll with a timeout and only exit
  once producers have finished *and* the queue is empty.
- Retry re-queuing moved outside the retry-counter lock, so a full queue
  blocking one consumer can't also stall every other consumer's retry
  accounting.

No change to what gets scraped, retry semantics, or the CLI flags.

## Verification

- Updated unit tests, including one asserting the queue is bounded and one
  asserting a consumer does not exit while the queue is momentarily empty
  but producers are still running (the pipelining fix itself).
- Full suite: 152 passed, 95.69% coverage (≥ 90% required); `ruff format`,
  `ruff check`, and `ty check` all clean.

## Residual recommendation

Prefer the default `num_threads=4` rather than increasing it — memory now
scales with `num_threads * 10` in-flight documents, not with `--span`. A
very large `--span` is still a long-running job on a small VPS, just no
longer one that can exhaust memory.

2026-08-10 update: producer batch size/thread count itself now also
scales with `num_threads` instead of a hardcoded 10 (see
`barrins-scripture-mtgtop8-oom-incident.md`'s note), so this
recommendation is now doubly true — raising `num_threads` grows both the
in-flight queue *and* each producer batch.
