# v1.0.0 "WorldWake" — Release Retrospective

The first-ever production release of the Barrin's ecosystem monorepo.
Before it, `main` contained only the initial GitHub Pages scaffold — no
application code had ever reached production, and no release tag existed.
This page sums up the whole effort — 14 work items tracked internally as
`proj/v1.0.0-bump` — across item boundaries: a timeline, milestones,
cross-cutting challenges (and how they were fixed), key data, and a set of
suggested [Constitution](https://github.com/Spigushe/barrins-project/blob/staging/.claude/CLAUDE.md)
amendments grounded in what the release actually surfaced.

Each work item's full implementation detail (design, tasks, UAT,
non-regression tests) is kept in the repository's internal project
tracking (`docs/project/first_production_release/`), reviewed via PR like
any other change but not published here — this page is the synthesized,
public-facing summary of that tracking, written once every item closed.

## Challenges, and how they were fixed

What's worth surfacing here is the handful of problems that **recurred
across independently-worked items** — that repetition is itself the
signal, not each individual instance.

### 1. jsdom doesn't implement the browser APIs Radix/cmdk components need

The sharing-extraction work needed `hasPointerCapture`/`scrollIntoView`
polyfills in the frontend's shared test setup for Radix `Select` to work
under Vitest/jsdom. The deck-selector rewrite, built independently right
after, hit the same category of gap with `cmdk`'s `ResizeObserver`
requirement. Both landed in the same shared test-setup file, so the fix
compounds — but the fact it was rediscovered rather than anticipated is
the actual finding.

### 2. Health-check failure mode: connection-level errors vs. query-level errors

`/health`'s original implementation only caught the SQLAlchemy error type
that wraps failures *after* a database connection is established. A fully
unreachable database (connection refused) surfaced as a raw driver
exception and an unhandled `500` instead of the intended `503`. Found only
via manual testing (blocking staging database access), not by the unit
tests written alongside the feature. Fixed by widening the exception
handling to catch any failure, with a dedicated regression test added for
the unreachable-database case specifically.

### 3. Frontend swallows API errors silently — a recurring pattern, not a one-off

The Moxfield-import UI never caught its import mutation's rejection, so an
invalid-URL error from the backend vanished in the browser instead of
reaching the user. This is the *same class* of bug already guarded against
on the login and email-verification pages — meaning the missing-error-
handling pattern had already been identified and fixed once, but wasn't
applied consistently to every new form using a mutation.

### 4. State that isn't scoped or re-synced correctly — only caught by manual testing

The deck-selector rewrite surfaced three separate bugs, all in the same
family (state that should follow "the currently active personal deck" but
didn't), none caught by the frontend's green automated suite that existed
before manual testing:

- Tab navigation links were hidden until a deck was selected, but the
  routed page content underneath wasn't — a fresh account landing
  directly on a content page still saw full data with no deck selected.
- A match-logging form's "My Deck" field only synced to the active deck on
  mount; switching decks afterward left it stale.
- Two report endpoints had no per-deck filter at all, unlike a sibling
  endpoint that already scoped correctly — cross-deck data leaked into
  the match log and archetype breakdown.

The third bug is notable: the correct pattern already existed one endpoint
over, and wasn't applied by comparison until manual testing forced the
question.

### 5. Ansible tooling has silent-failure modes that look like success

Recurring across the backup role and the docs-deployment playbook work,
both traced back to the same root cause (`ansible-lint` behaves
differently depending on the working directory it's invoked from):

- `ansible-lint` run from inside `ops/my-server` silently processes **0
  files** while still printing "Passed" — indistinguishable from a real
  clean run unless the file count is checked. It must be run from the
  repository root, exactly matching CI.
- The docs-deployment playbook shipped with a stray `become: false`,
  copied from a pattern used by a different role — it broke the deploy
  with a permissions error, because this role builds as root unlike the
  role it was copied from. The pattern was copied without re-checking the
  assumption it depended on.
- A shared, intentionally-unprefixed fact tripped `ansible-lint`'s
  variable-naming rule — fixed with a targeted suppression, since the
  rule has no legitimate exception path for a fact deliberately shared
  across roles.
- This site's own CI job wasn't actually running for part of the release
  (a paths-filter output was missing one flag), found and fixed only in a
  post-merge follow-up, after most of the release had already merged
  without it catching anything.

### 6. Planning assumptions drifted from actual repo state, in both directions

- The `1.0.0` version bump was initially believed already committed on
  `staging`, from an earlier check that read an uncommitted working-tree
  edit as if it were real. It wasn't — it was real, separate work.
- Conversely, the Moxfield backend work assumed its frontend field still
  needed to be built and deferred it to the deck-selector item. It turned
  out to already exist, discovered only while wiring that later item — the
  only work needed was renaming a stale placeholder function.
- The API routes reorganization wasn't planned at all. It emerged mid-way
  through the Moxfield work, once a naming inconsistency became visible
  while adding a new route.

Each case was caught before it caused damage, but each was caught by a
person actually looking, not by process. Three independent instances of
"the plan's belief about current repo state was wrong" in one release is
enough to be a pattern, not noise.

### 7. Scope decided mid-flight, reversed once evidence appeared

An opponent-deck quick-create feature was initially deferred: defaulting
its category/tier fields for a hand-created entry looked like the
frontend fabricating an analytical claim it had no basis for. It was
reinstated after review, once an existing similar form elsewhere in the
codebase was found to already default those exact fields the same way —
the objection dissolved once local precedent was checked, but the check
only happened because someone pushed back on the initial deferral.

### 8. Known issues, explicitly deferred rather than silently dropped

- **Changelog aggregation heading levels**: sub-repo and Keep-a-Changelog
  category headings render at the same nesting level in this site's
  "Latest changes" section. Cosmetic, not a release blocker — tracked in
  [Roadmap](../roadmap.md) for the next release.
- **Root README's real links** (to this docs site and the production
  apps) were deliberately left out until the production deploy actually
  shipped, to avoid a public README advertising links that didn't work
  yet.

## Key data

- **14/14 work items** shipped, each fully UAT-confirmed before merge.
- **Backend**: 237/237 tests passing, 98.21% coverage at release time
  (against a 60% cumulative-coverage floor required per item throughout
  the release).
- **Frontend**: 54/54 tests passing.
- **Ops**: `ansible-lint` clean under the strict `production` profile —
  from 114 pre-existing failures down to zero, before this release even
  started.
- **≥8 concrete defects** found and fixed via manual testing or CI rather
  than by the unit tests written alongside each feature — see Challenges
  above. One further issue (the changelog heading-level bug) was found but
  explicitly deferred, not fixed.
- **New external dependency**: HetrixTools (a monitoring account, not a
  code dependency).
- **New frontend dependencies**: `@radix-ui/react-popover`, `cmdk` —
  approved against the Constitution's dependency policy, small and
  well-maintained, matching how other Radix-based components are already
  built in this project.
- **New backend dependencies**: none.
- **Decision Records**: 4 ADRs exist after this release — secrets never
  committed and release-tag-only production deploys (both pre-existing),
  plus two added during this release: transactional email, and the
  backup/monitoring/Moxfield-secret bundle (ADR-4). See
  [Decision Records](../architecture/decisions.md).
- **Scope deliberately excluded**: the dedicated identity service
  (mid-implementation, unmerged) and Tolaria News (no application code
  yet) — see [Roadmap](../roadmap.md) for what that means for the next
  release.

## Suggested Constitution amendments

These are proposals, not applied changes — the
[Constitution](https://github.com/Spigushe/barrins-project/blob/staging/.claude/CLAUDE.md)
itself requires subjective architectural or process decisions to stop for
a user decision rather than being silently adopted (§5, §16.2). Each
proposal below is grounded in a specific, repeated pattern from this
release, not a hypothetical.

1. **§19 (Testing Requirements): add a "scoping/filter parity" check.**
   This release's most concerning bug (two report endpoints missing a
   filter a sibling endpoint already had) was a case where the correct
   pattern already existed one endpoint over. Suggest adding to §19.2:
   *"When adding a new endpoint alongside existing sibling endpoints over
   the same resource, verify it applies the same scoping/filter parameters
   they do — a missing filter is a data-leak class of bug, not a cosmetic
   gap, and existing siblings are the first place to check."*

2. **§14 (Frontend Standards) / §19.3: codify the jsdom polyfill
   requirement.** Two independent items this release rediscovered that
   Radix-based components need jsdom polyfills. Suggest a line in §14.3 or
   §19.3: *"Components built on Radix primitives or `cmdk` commonly
   require jsdom polyfills not present by default (`hasPointerCapture`,
   `scrollIntoView`, `ResizeObserver`) — check the shared test setup for
   the existing list before assuming a new component test failure is a
   real bug."*

3. **§26.4 (Ansible standards): promote the `ansible-lint`
   working-directory gotcha from a tip to a stated rule.** It's already
   partially documented there; this release hit it again in a second,
   independent item, which suggests the current phrasing isn't enough to
   prevent rediscovery. It silently reports "Passed" while linting
   nothing — the failure mode that makes it dangerous.

4. **§16.1 (Development Workflow), step 1: add an explicit
   re-verification sub-step.** Three separate instances this release (the
   version-bump status, the Moxfield frontend field, and generally
   treating a plan's own prior description as authoritative about
   "already done" work) trace back to the same root cause: a plan's belief
   about current repo state wasn't re-checked against the actual branch
   before starting. Suggest appending to step 1 ("Understand the
   requirement"): *"If the requirement or its plan asserts something is
   already done (a prior commit, an existing field, a completed
   dependency), verify that assertion against the actual target branch
   before starting — do not treat a plan's description of past state as
   ground truth."*

5. **§36 (Backup Strategy): state the release-gating consequence
   explicitly, not just the general principle.** §36 already says "a
   backup that has never been tested is not considered reliable," and this
   release correctly treated that as a release blocker in practice (see
   ADR-4). Since this was the first time the principle was actually
   load-bearing, suggest making the consequence explicit in §36 itself:
   *"No production deployment that could apply a database migration may
   proceed until a backup mechanism exists for that database and a
   restore drill has been personally performed and verified — not just
   documented."* This turns this release's ad hoc sequencing decision into
   a standing rule for every future service, not something re-derived per
   release.

6. **New subsection under §21 (Documentation Requirements): "immature
   feature gating."** This release's pattern for the sharing feature —
   extract the immature part into its own component, gate it behind a
   simple constant rather than building a full feature-flag system, and
   still add the missing test even while disabled — is a reusable,
   low-ceremony answer to "ship anyway vs. hide it" that a future release
   will likely face again for some other in-progress feature. Worth
   writing down once rather than re-deriving.

7. **§30/§31.2 (TLS/Monitoring): record the provider-selection criteria
   used, not just the requirement.** ADR-4 used explicit criteria (free
   tier, minimal signup PII, private status page by default) to choose a
   monitoring provider. Suggest folding those criteria into §30/§31.2
   directly, so a future monitoring decision (e.g. once the current
   provider's tracker cap is hit, per [Roadmap](../roadmap.md)) starts from
   a stated standard instead of re-litigating from scratch.

None of these are blockers for anything currently shipped — they're
process refinements based on what this release actually surfaced. If
adopted, they'd be edits to the
[Constitution](https://github.com/Spigushe/barrins-project/blob/staging/.claude/CLAUDE.md)
itself.
